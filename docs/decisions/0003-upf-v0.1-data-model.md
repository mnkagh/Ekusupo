# ADR-0003: UPF v0.1 Data Model

Status: Accepted

## Context

UPF (CLAUDE.md §5) is the canonical internal representation everything else
in Ekusupo depends on, but §5.4 explicitly says "the exact schema must be
defined in dedicated documentation before production implementation" — that
documentation didn't exist yet. This ADR records the data-model decisions
made while writing `docs/universal-playlist-format.md` and implementing
`packages/upf`, including the alternatives considered for each, per
CLAUDE.md §18.3 (ADRs for decisions affecting the data model).

## Decision

1. **Scope**: v0.1 is playlists-only (`UpfDocument.playlists`). No
   standalone library-collection modeling yet.
2. **Internal identity**: every core entity gets a UPF-native `id: string`,
   separate from `externalIds` (ISRC/UPC) and `providerRefs[*].id`
   (provider-specific ids). ID _generation_ is explicitly left
   unspecified — a data-model concern about identity, not about algorithm.
3. **Provider references are fully generic**: `providerRefs?: Record<string,
ProviderRef>`, keyed by an arbitrary runtime string, never a closed
   TypeScript union of known providers.
4. **Denormalized/embedded shape**: entities are embedded inline
   (`PlaylistItem.track`, `Track.album`, `Track.artists`/`Album.artists`)
   rather than stored once and referenced by id.
5. **Explicit content is a tri-state**: `"explicit" | "clean" | "unknown"`.
6. **Duration in integer milliseconds.**
7. **Artists are ordered arrays**, first entry = primary artist.

## Alternatives Considered

- **Normalized storage** (`playlists` + `tracks: Record<id, Track>` +
  `albums: Record<id, Album>` lookup tables, with playlists/tracks
  referencing by id) — rejected for v0.1. More storage-efficient for large
  exports with repeated tracks/albums, but works against UPF's own stated
  design goals (§5.2: human-readable, suitable for debugging) — a reader
  has to cross-reference three tables to understand one playlist item.
  Worth revisiting if document size becomes a real problem once real
  exports exist.
- **Boolean `explicit` flag** — rejected. Silently coerces "provider didn't
  say" into `false`, which is a false claim, not a default.
- **Duration in seconds** (float or integer) — rejected in favor of integer
  milliseconds, mainly for precision headroom in future duration-tolerance
  matching (§10.2), and because it's the more common provider-API
  convention to convert from.
- **Closed provider union type** (e.g.
  `type ProviderId = "spotify" | "apple-music" | "youtube-music"` used as
  the key type for `providerRefs`) — rejected outright; this would make
  `packages/upf` itself provider-aware, directly violating CLAUDE.md §3.1.
  Every provider name in the system must be a runtime string, never a type.
- **Modeling match confidence/history now** (CLAUDE.md §5.3 lists it as
  something UPF should "eventually represent") — deferred. It's Matching
  Engine output, not portable-format input, and that engine doesn't exist
  yet; adding placeholder fields now would be designing blind. Revisit once
  CLAUDE.md's Matching Engine phase is underway.
- **Including library collections in v0.1** — considered and explicitly
  rejected after discussion; deferred to v0.2 once a real connector/transfer
  use case exists to drive the actual shape needed, rather than guessing at
  it now.

## Consequences

- `packages/upf` v0.1 has zero references to any specific music provider
  anywhere in its types — verified by grepping the package source for
  provider names.
- Adding a new provider's data to UPF never requires a UPF schema change;
  it only ever populates a new key in an existing `providerRefs` map.
- Large exports (e.g. a library with many playlists sharing the same
  album/artists) will have real duplication in the JSON. Acceptable at this
  stage; revisit if/when it's an actual problem.
- The envelope (`UpfDocument`) will need a breaking (or additive, if done
  as an optional field) change when library collections are added in v0.2 —
  anticipated and accepted, not treated as a design flaw of v0.1.
